> **Prompt**: When should I use a struct instead of a class?

In C#, the decision between a `class` and a `struct` comes down to one core question: **Are you modeling an independent entity with its own lifecycle, or are you just bundling a few related values together?**

By default, you should almost always use a `class`. However, you should switch to a `struct` when you need to optimize memory and reduce Garbage Collection overhead for small, simple data structures (like 2D coordinates, RGB colors, or time intervals).

To understand why, you have to look at how they live in memory.

---

## 1. The Memory Difference: Value vs. Reference

* **Classes are Reference Types:** When you create a class, the actual data is stored in the **Heap** (a large pool of memory). A small pointer (reference) is placed on the **Stack** to keep track of where that data is. When you are done with it, the Garbage Collector has to clean it up.
* **Structs are Value Types:** When you create a struct, the actual data is stored directly on the **Stack** (or inline inside whatever object contains it). There is no pointer, and there is no Garbage Collection overhead. When the method finishes, the memory is instantly freed.

---

## 2. Microsoft's 4 Golden Rules for Structs

Because structs are copied entirely every time you pass them to a new method, using them incorrectly can actually make your application *slower*. Microsoft recommends you only use a `struct` if your type meets **all four** of these criteria:

1. **It logically represents a single value.** (Just like an `int` or a `double` does).
2. **It has an instance size under 16 bytes.** (A `decimal` is 16 bytes. Two `double` properties are 16 bytes. If it's larger than this, copying the struct back and forth becomes more expensive than just using a class reference).
3. **It is immutable.** (Once you create it, the data should never change).
4. **It won't be boxed frequently.** (Boxing happens when you are forced to cast a struct into an `object` or interface type, which forces it onto the Heap anyway, defeating the purpose).

---

## 3. Code Example: Good vs. Bad Structs

Here is an example of the perfect use case for a struct, and a scenario where it becomes dangerous.

**The Perfect Struct:**

```csharp
// GOOD: Small (8 bytes), immutable, logically a single value.
public readonly struct GpsCoordinate 
{
    public double Latitude { get; }
    public double Longitude { get; }

    public GpsCoordinate(double lat, double lon) 
    {
        Latitude = lat;
        Longitude = lon;
    }
}

```

*Note: Using the `readonly` keyword explicitly enforces rule #3 at the compiler level, which is a modern C# best practice.*

**The Bad Struct (Use a Class instead):**

```csharp
// BAD: Way too large, contains string references, and models an entity.
public struct Customer 
{
    public Guid Id { get; set; }        // 16 bytes
    public string Name { get; set; }    // 8-byte pointer
    public string Address { get; set; } // 8-byte pointer
    public DateTime Created { get; set; } // 8 bytes
}

```

If you pass this `Customer` struct to 5 different methods, C# has to physically copy 40 bytes of data into memory 5 times. If it were a `class`, it would only copy an 8-byte reference pointer.
