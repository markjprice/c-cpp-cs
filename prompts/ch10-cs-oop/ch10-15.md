> **Prompt**: Please explain the difference between classes, structs, and records in modern C#. Why are records popular in modern C# APIs? Show how value equality works in records.

In modern C#, you have three main ways to define a complex type: a `class`, a `struct`, or a `record`. While they look similar on the surface, they are designed to solve fundamentally different problems regarding memory, mutability, and equality.

Here is the quickest way to categorize them:

* **Classes** are for modeling **behavior and entities** (things that have a distinct identity and change over time).
* **Structs** are for modeling **small, mathematical values** (like an XY coordinate or a color).
* **Records** are for modeling **immutable data** (things that just hold information and shouldn't change).

---

## 1. Why are Records so Popular in Modern APIs?

When you build a modern API, you are constantly sending and receiving data (usually converted to JSON). This data is typically mapped to Data Transfer Objects (DTOs).

Records became incredibly popular for APIs because they solve three major headaches perfectly:

**A. Boilerplate Reduction**
APIs require hundreds of DTO classes. With traditional classes, you have to write properties, constructors, and assignments. With records, you use a **primary constructor**, reducing a 15-line class to a single line:

```csharp
// The old way (Class)
public class UserDto 
{
    public string Name { get; }
    public string Email { get; }

    public UserDto(string name, string email) 
    {
        Name = name;
        Email = email;
    }
}

// The modern API way (Record)
public record UserDto(string Name, string Email);

```

**B. Built-in Immutability**
When data comes into your API, you shouldn't be changing the payload mid-flight—that causes bugs. Records (using the primary constructor syntax above) are entirely immutable by default. You can read `user.Name`, but you cannot reassign it.

**C. Non-Destructive Mutation**
If you *do* need to modify a record's data, C# provides the `with` keyword. It creates a brand-new copy of the record with only the specified fields changed, leaving the original data perfectly safe.

```csharp
var original = new UserDto("Alice", "alice@test.com");
var updated = original with { Name = "Alice Smith" }; 

```

## 2. Value Equality vs. Reference Equality

The most powerful feature of a `record` (and what separates it from a `class`) is how it answers the question: *"Are these two things equal?"*

* **Classes use Reference Equality:** They check if two variables point to the exact same physical spot in the computer's memory. Even if they have the same data, they are not equal if they are two separate objects.
* **Records use Value Equality:** The compiler automatically writes a ton of hidden code for records that checks the actual *data* inside. If the data matches, the records match.

Here is how that looks in practice:

```csharp
// --- The Class Behavior ---
public class CarClass 
{
    public string Make { get; set; }
    public string Model { get; set; }
}

var car1 = new CarClass { Make = "Honda", Model = "Civic" };
var car2 = new CarClass { Make = "Honda", Model = "Civic" };

// This is FALSE. 
// They are identical in data, but they live in different memory locations.
Console.WriteLine(car1 == car2); 


// --- The Record Behavior ---
public record CarRecord(string Make, string Model);

var record1 = new CarRecord("Honda", "Civic");
var record2 = new CarRecord("Honda", "Civic");

// This is TRUE. 
// The record ignores memory addresses and strictly compares the data (Honda == Honda).
Console.WriteLine(record1 == record2); 

```

This built-in value equality makes testing APIs and comparing incoming payloads infinitely easier, which is why `record` is the modern standard for data-holding objects.
